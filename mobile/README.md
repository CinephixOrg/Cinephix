# Cinephix Mobile — Handoff / Status Document

This document exists so a second developer (and their AI assistant) can pick up this codebase cold and understand what exists, why it's built the way it is, and what's left. It reflects the actual state of the code as of this write-up — read it alongside the code, not instead of it.

## 1. What this is

A React Native (Expo) port of the Cinephix web app (`frontend/`), talking to the same backend (`backend/`, Express + MongoDB) — no backend changes were needed except two small additions for mobile Google Sign-In (see §7). The web app is the source of truth for behavior; this app mirrors it feature-by-feature rather than reinventing anything.

**Stack**: Expo SDK 57, Expo Router (file-based routing), TypeScript, plain `StyleSheet` (no NativeWind/Tailwind — see §8 for why), `expo-secure-store` for auth, `axios` for API calls.

**Not started from a prior attempt**: an earlier AI-assisted attempt at this port existed but never produced working code — everything in `mobile/` today was built fresh in this session, verified against the real backend on a physical Android emulator.

## 2. Prerequisites & running it

- Node + npm, Android Studio (for the emulator) or a physical Android phone with Expo Go installed.
- `backend/.env` must be filled in (Mongo URI, JWT secret, Cloudinary, Google OAuth client ID/secret — see `backend/.env.example`).
- `mobile/.env` (gitignored — copy from `mobile/.env.example`):
  ```
  EXPO_PUBLIC_API_BASE_URL=http://<value>:5000/api
  ```
  **This value depends on how you're testing** — this trips people up:
  - Physical phone (same Wi-Fi as your PC): your PC's LAN IP, e.g. `http://192.168.1.105:5000/api` (find via `ipconfig`).
  - Android Studio emulator: `http://10.0.2.2:5000/api` — the emulator's special alias for "the host machine." `localhost` from *inside* the emulator refers to the emulator itself, not your PC.
  - Env vars are read once when `expo start` boots — changing `.env` requires restarting the dev server, not just reloading the app.

**To run**:
```
# terminal 1
cd backend && npm run dev
# terminal 2
cd mobile && npx expo start
```
Press `a` to launch on a connected emulator, or scan the QR with Expo Go on a physical phone (same Wi-Fi). If you add/change a native dependency, restart with `npx expo start --clear` (stale Metro cache is a common source of confusing "unable to resolve module" errors right after `npm install`).

**Windows npm quirk**: `npx expo install <pkg>` sometimes fails with an `ERESOLVE` peer-dependency conflict caused by `expo-router`'s optional web-target dependencies (`@radix-ui/*` via `vaul`) — unrelated to whatever you're installing. Workaround: `npm install <pkg>@<expo-recommended-version> --legacy-peer-deps`. This has been consistently reproducible, not a one-off.

## 3. What's built (functionally complete, tested on-device)

### Auth
- Email/password: register → verify-email (6-digit code) → login. Token stored in `expo-secure-store`, not `localStorage` (mobile equivalent).
- Google Sign-In: in-app-browser OAuth flow reusing the backend's existing Passport setup (see §7 — this took real debugging, read it before touching auth).

### Movies / Series tabs
Infinite-scroll browse + search-as-you-type (via the list endpoints' `title`/`query` filter params, not the separate `/search` endpoints — those return a differently-shaped payload; using the filter param keeps one consistent shape everywhere).

### Content Detail
Poster, overview, TMDB rating, 5-star rating input (see §8 — half-star granularity matching the web widget, backed by the same 1–10 integer scale), Add-to-Watchlist toggle, Add-to-List (modal, multi-select against your lists, inline create-new-list).

### Watchlist tab
Same infinite-list pattern, pull-to-refresh.

### Lists ("Custom Lists") tab
My Lists (create/delete), List Detail (view items, owner-only edit name/description/visibility, remove item). **Not built**: the web's "Discover public lists" (web itself has no dedicated page for this either — only a homepage widget — so there was nothing to port), bulk multi-select add-from-browse (web's `AddItemsToListModal` — single-item add via Content Detail covers the core use case).

### Profile tab
View own profile (avatar, username, bio, follower/following counts — tappable, opens a list of who they are), CineGraph as an actual interactive donut chart (tap a slice or legend row to see that genre's exact count + %, not just bars — see §8), Edit Profile (bio/username, avatar via native image-picker crop UI), Settings (password change — hidden for Google accounts, privacy toggle, logout, delete account).

### Cinematch tab
Taste-matching against other users: `POST /api/match` (discovery, filter by genre/watched-count/avg-rating) and `POST /api/match/:id/analyze` (LLM narrative comparison). New 6th bottom tab, deliberately not nested under Profile (overriding the original plan's own suggestion). "View Profile" from a match result and "Share analysis to DM" are both deliberately not built — no other-user-profile screen exists yet, and DM sharing depends on Chat (below), which shipped after Cinematch. `POST /api/match/:id` (specific-pair) and `GET /api/match/compatibility/:id` (referenced by web but no backend implementation — confirmed dead route, not a spec gap) are intentionally not used.

### Notifications
Global `NotificationContext` polls `GET /notifications/unread/count` every 10s while logged in (mirrors web — there's no socket push for the general badge on web either). A bell+badge sits in the header of every tab's root screen; the notifications list itself (`app/notifications.tsx`) is a **root-level modal route**, not duplicated per-tab like Content Detail, since it isn't reachable from inside any tab's own Stack. Tapping a notification only marks it read — no navigation — because every one of web's tap targets (DM screen, another user's profile, follow-request management) was itself unbuilt at the time; revisit once those exist.

**Navigation sharp edge hit here, worth remembering for any future root-level route**: the root `<Stack>` in `app/_layout.tsx` originally had zero explicit `<Stack.Screen>` children (fully auto-discovered). Adding just one explicit child (`notifications`) without also explicitly declaring the others broke routing entirely — the app booted straight into the modal with no way to reach anything else. Fix: once you add any explicit `Stack.Screen`, declare **all** of that Stack's screens, not just the new one.

### Chat (DMs) and Community/Groups
One global `ChatContext` (`socket.io-client`, single app-wide socket — deliberately consolidates what's two separate sockets on web into one) backs both. Auth via `io(url, {auth:{token}})`, not a header. The socket disconnects on backgrounding and reconnects+refetches on foreground (no push-notification infrastructure exists in this project, so a backgrounded socket does nothing useful anyway). Optimistic send uses a `clientTempId` reconcile pattern ported from web's `useChat.js`.

- **Chat** — DM messaging. `GET /conversations` returns DM+group rows merged with no server filter, so `conversationService.getConversations()` filters to `type==="dm"` client-side. Message pagination has its own cursor-based envelope (`{hasMore,limit,before}`), different from the `{total,page,limit,pages}` shape used everywhere else — has its own `MessagePagination` type, don't reuse the generic one. Only plain-text compose exists; `recommendation`/`analysis_share` message types render read-only if received. **Originally its own 7th tab at `app/(app)/messages/`; since merged into the unified Socials tab — see "New unified Socials tab" below for the current route locations.**
- **Community/Groups** — directory with category chips, group detail with Chat/Members/About tabs. `ChatContext.joinRoom/leaveRoom/sendMessage` were generalized to take a `roomType: "dm" | "group"` param for this. The actual chat UI (message list, composer, pagination) was extracted into a shared `src/components/ChatRoom.tsx` used by both DM and group screens — socket room-join/leave lifecycle stays owned by each parent screen since they have genuinely different correct lifecycles (DM screens stay mounted on blur, so use `useFocusEffect`; a group's Chat tab actually mounts/unmounts with tab switches, so a plain `useEffect` is correct there). No group-creation UI — no backend endpoint for it; groups are preset/seeded. Two web bugs fixed rather than ported: web's group message pagination silently drops the cursor (no working "load older" for groups on web at all), and web's group screen reuses a stale message snapshot instead of refetching per visit. **Originally its own 8th tab at `app/(app)/community/`; since merged into the unified Socials tab — see "New unified Socials tab" below for the current route locations.**

### i18n
Full app coverage (not just web's own partial coverage) in all 12 of web's locales (en/tr/ru/ja/zh/fr/ko/ar/it/es/de/pt) via `i18next` + `react-i18next` + `expo-localization` (RN has no drop-in equivalent to web's `i18next-browser-languagedetector`, so `src/i18n/index.ts` hand-resolves: persisted override → device locale → `en` fallback, persisted via the existing `expo-secure-store`). Switcher lives in `profile/settings.tsx` (web's lives in a persistent `TopBar` dropdown; mobile has no persistent global chrome). Key convention **mirrors web exactly** — the raw English string is the key itself (`t("Movies")`, not `t("nav.movies")`) — this let ~85 already-translated keys be lifted verbatim from `frontend/src/locales/index.js`; ~94 net-new mobile-only keys were hand-authored directly rather than machine-translated (web's own translation pipeline, `@vitalets/google-translate-api`, is a flaky rate-limit-prone scraper unsuitable for bulk automated calls). **Genre names and group tags are deliberately NOT translated** — they're literal values sent to backend filter/query params; translating the display would break API matching. Don't "fix" this without checking first.

### Polish — loading skeletons
`src/components/Skeleton.tsx`: a pulsing `SkeletonBox` primitive (opacity loop via RN's built-in `Animated` API — `react-native-reanimated` isn't installed and isn't needed) plus shape-matched composites (`SkeletonRow`, `SkeletonListRow`, `SkeletonGrid`, `SkeletonPosterCard`, `SkeletonGroupCard`, `SkeletonAvatarCell`, `SkeletonProfileHeader`, `SkeletonGroupDetailHeader`, `SkeletonChatBubbles`, `SkeletonMatchResults`), swapped in for `ActivityIndicator` across every full-content-load screen. Two real gaps were filled along the way, not just re-skinned: Cinematch previously showed nothing while searching (now mirrors web's `MatchLoadingAnimation` podium+grid shape), and the Messages inbox had no loading state at all (now has one). Submit-button "action in progress" spinners were deliberately left as plain `ActivityIndicator` — skeletons are for initial content load, not action feedback. **Offline handling was not built** — see §5.

### Home tab
**Superseded (2026-08-12) by the "Home redesign" entry further down** — this section documents the screen's original flat-rail implementation for history; the nested-Stack rationale in the 3rd paragraph below still applies unchanged to the redesigned screen, everything else here describes sections that no longer exist. New 9th tab, **first position** — replaces Movies as the post-login landing screen (`app/index.tsx`'s redirect now targets `/home`, not `/movies`). Ports 3 of web's 5 homepage sections: **Popular This Week** (`GET /api/feed/popular-this-week`, global watchlist-add aggregate over the last 7 days), **For You** (`GET /api/feed/recommendations`, genre-scored off the same CineGraph fields Cinematch/Profile already read — the section title flips to "Popular Right Now" when the response's `hasPersonalization` is false, matching web's own conditional subcopy), and **Discover Lists** (`GET /api/lists/discover`, public lists — followed users' lists first, then filled with community lists). All 3 pre-existed on the backend; no backend changes.

**Deliberately not ported**: Top Picks, Popular Reviews, the Activity-feed tab, and Suggested Users — all 4 depend on **Follow/unfollow**, **written reviews**, or **viewing another user's profile**, none of which exist in mobile at all (confirmed: `userService.ts` has no `follow()`, `connections.tsx`'s followers/following list is read-only, there's no review-text concept anywhere in the mobile codebase). Building those would mean building three unrelated features first — deferred to a future "Social/Network" milestone.

Home has its **own nested Stack** (`home/_layout.tsx`, `home/content/[type]/[id].tsx`, `home/lists/[id].tsx`) rather than reusing Movies/Series/Lists' existing detail routes, per the Navigation architecture convention below — reusing another tab's route would silently switch your active tab on every card tap. This required extracting `src/screens/ListDetailScreen.tsx` out of what was previously inline in `lists/[id].tsx` (same self-contained pattern as `ContentDetailScreen.tsx`); it takes an optional `basePath` prop (`"/lists"` default, `"/home"` when opened from Home) forwarded to its own item grid's `ContentCard`s, so a list's contents stay within whichever tab's Stack opened it.

New `src/components/ContentRail.tsx` — the first horizontal poster-rail pattern in the app (everything else is a grid or vertical list) — is a generic `{title, data, renderItem}` wrapper backing all 3 sections. `src/components/DiscoverListCard.tsx` is the compact horizontal list card. The Discover Lists "from someone you follow" badge reuses the existing `t("Following")` i18n key rather than adding a new one — confirmed web's own `PublicListCard.jsx` does the same dual-context reuse.

### Follow/Network + Public Profile
Closes what was the single highest-leverage remaining gap — unblocked Reviews' "Friends" tab, Favorites' profile display, Home's Top Picks/Popular Reviews/Activity-feed, Cinematch's "View Profile", and Notifications' `follow`/`follow_accepted`/`follow_request` tap targets, all previously deferred specifically because this didn't exist.

Two **root-level** routes (not per-tab — see the Navigation architecture section below for why): `app/user/[id].tsx` (Public Profile: avatar, bio, stats, CineGraph donuts, follow button — **Favorites section intentionally omitted**, since Favorites isn't built yet, revisit when it ships) and `app/network.tsx` (Followers/Following/Requests tabs + a Suggestions rail, **replaced** the old read-only `profile/connections.tsx` entirely — now supports viewing *any* user's connections via `?userId=`, not just your own).

**No shared follow-button abstraction exists on web** — follow logic is duplicated 3x (`NetworkPage.jsx` main list, its Suggestions sidebar, and `PublicProfilePage.jsx` each reimplement their own Follow/Unfollow/Requested button). Mobile got one built fresh: `src/context/FollowGraphContext.tsx` (app-wide "who do I follow / who have I sent a request to" ID sets, so following someone in Suggestions is instantly reflected in Network without a refetch) + `src/hooks/useFollowState.ts` + `src/components/FollowButton.tsx`. **Deliberate small UX deviation from web**: tapping the "Requested" state cancels the request (web leaves it disabled/inert) — same backend call either way (`unfollow` doubles as "cancel my sent request", there's no dedicated cancel endpoint).

Wired up the 3 small integrations this unblocked, since none of them need Reviews/Favorites: Notifications now actually navigate on tap (`follow`/`follow_accepted` → Public Profile, `follow_request` → Network's Requests tab, `message` → the DM conversation screen — previously mark-read-only); Cinematch's `MatchCard` got its "View Profile" button back; Home got a new Suggested Users rail (`src/components/SuggestedUserCard.tsx`, reused by both Home and Network's Suggestions rail).

**Backend fix included**: `getMyFollowing`/`getMyFollowers` (`backend/controllers/userController.js`) had no privacy gating on their `?userId=` param — any authenticated user could list a *private* account's followers/following, even though the profile endpoint itself correctly blocks that. Now gated with the same `isAuthorizedToView` helper the profile endpoint already uses. The same refactor fixed a pre-existing bug where `getMyFollowers`'s `pagination.total` was computed from the *viewer's* own follower count instead of the target's when viewing someone else's followers.

`GET /users/profile/:id` has two real response shapes (full vs. masked-for-private) and is entirely raw (no envelope) — modeled in `src/types/index.ts` as a discriminated union (`PublicProfileFull | PublicProfileMasked`) on `isAuthorized`. Several of the other follow endpoints have their own inconsistent envelopes too (raw `{success,message}` with no `data` key, or bare arrays with no envelope at all) — see §4 and the per-function comments in `src/api/userService.ts` before adding more.

### Reviews
Write/edit (single upsert form — resubmitting just re-saves, no separate edit-mode UI, matching web), delete (no confirmation dialog, matching web), and like/unlike, added to Content Detail (`src/screens/ContentDetailScreen.tsx`: a new "Your review" section right after Overview, then Friends/Popular tabs below it). Also un-deferred Home's "Popular Reviews" rail (skipped when Home first shipped) — it **renders nothing at all when empty**, matching web's `PopularReviews.jsx` exactly, a genuine behavioral difference from Home's other 4 rails (which all show empty-state text).

New `src/components/UserAvatar.tsx` — mobile's first shared avatar-circle+tap-to-profile component. Reviews needed it in 2 new places, which would have made it the 6th/7th near-identical inline implementation (`network.tsx` already has 2, plus `SuggestedUserCard.tsx`, `user/[id].tsx`, `DiscoverListCard.tsx`) — past the point where extraction pays for itself. **The 5 pre-existing sites were deliberately left un-retrofitted** in this pass (unrelated churn against code that shipped very recently) — any *future* avatar call site should use `UserAvatar`, not inline a new copy.

New `src/hooks/useMyReview.ts` — there's no "my review for this content" backend endpoint; it scans `GET /reviews/content/:id` client-side for the logged-in user's own entry, the same approach web's `ContentDetailPage.jsx` uses (`fetchUserReview`), just packaged as a reusable hook instead of inlined per-screen.

Content Detail's review fetch is **deliberately separate** from its existing content/rating/watchlist `Promise.all` — that one drives the screen's single fatal `loading`/`error` state, and a reviews-API hiccup shouldn't block viewing the poster/rating/watchlist. Reviews get their own small effect with a non-fatal try/catch (defaults to empty arrays on failure) — this also matches web's actual architecture more closely (its `ReviewSection` has independent `loadingFriends`/`loadingPopular` state, separate from the main content fetch).

**Backend fix included**: `Review.text` is capped at `maxlength: 2000` in the Mongoose schema, but both the validation middleware and the controller's manual check were enforcing `5000` — a 2001–5000 char review passed app-level validation then threw an uncaught Mongoose `ValidationError` on save (likely surfacing as a 500 instead of a clean 400). Fixed both checks to `2000` to match the schema (the actual persisted limit, and the correct source of truth here — not the looser app-level checks). Unlike Follow/Network, every review backend endpoint uses the clean standard `{success,message,data,pagination?}` envelope — no special-casing needed in `src/api/reviewService.ts`.

**Found and fixed in passing**: `ContentDetailScreen.tsx` had *zero* i18n coverage — every string on it was hardcoded English, despite the i18n milestone's "full app coverage" claim (§3). This was a pre-existing gap in that milestone, not something introduced here. Wrapped its ~12 existing hardcoded strings in `t()` while already deep in this file for the new review UI, so the screen isn't left half-translated.

### Favorites
Editing is **Content-Detail-only**, matching web exactly — neither Profile screen has an edit entry point. A 3rd button in `ContentDetailScreen.tsx`'s action row ("Add to Favorites"/"Manage Favorites") opens `src/components/FavoritesModal.tsx`: mobile's **first Save/Cancel batch-editing modal** (every other content-collection UI here — Watchlist, Custom Lists — saves per-tap immediately). Seeded with the user's existing favorites of that type + the current item, each removable via ✕, Save blocked with an inline error above the 5-item cap (movies and series have independent caps, enforced server-side). **Deliberately not ported**: web's side effect of silently force-adding the item to the Watchlist when the favorites modal opens — mobile's button does exactly one thing.

**The biggest structural change of this milestone**: `app/user/[id].tsx` (Public Profile) was converted from a flat file into a directory with its own nested Stack (`app/user/[id]/_layout.tsx` + `index.tsx` + `content/[type]/[id].tsx`), mirroring `(app)/home/`'s structure — necessary because Favorites is the first thing on Public Profile that links into Content Detail, and without its own Stack that tap would have to reuse some other tab's route (silently switching the active tab, exactly the failure mode the Navigation Architecture section below warns about). **Confirmed no collision** between the outer `user/[id]` segment (the viewed user's id) and the inner `content/[type]/[id]` segment (content id) despite sharing the name `[id]` — `useLocalSearchParams()` is scoped to the current focused screen only, not merged with ancestor route segments (that's `useGlobalSearchParams()`'s job); `lists/[id].tsx` + `lists/content/[type]/[id].tsx` already prove this exact pattern works elsewhere in this codebase, so `ContentDetailScreen.tsx` itself needed zero changes. Own Profile (`(app)/profile/`) got the simpler version of the same treatment — one new `Stack.Screen` + thin route added to its existing Stack, no restructure needed since it has no outer `[id]` segment to collide with.

`ContentCard`'s `basePath` union gained `"/profile"` and a template-literal `` `/user/${string}` `` — the first non-static `basePath` value, since Public Profile's own route is itself parameterized by the viewed user's id.

**Small fix in passing**: `ContentRail.tsx`'s outer `section` style was missing `alignSelf:"stretch"`, so it silently shrank to fit its content instead of spanning full width inside both Profile screens' `alignItems:"center"` containers (Home's own container has no such override, so this never surfaced there before). Fixed by adding it, matching the pattern `CineGraphDonut` already used to solve the identical problem on these same screens.

No backend changes needed this round — the 5-item cap (movies/series independent) was already correctly enforced server-side.

### Activity Log / Undo
New `app/(app)/profile/activity-log.tsx`, reached via a new row in `settings.tsx` between Language and Change Password. Mobile's **first multi-select list UI** — a `Set<string>` of selected log ids, `Ionicons "checkbox"/"square-outline"` per row (reused verbatim from `ContentDetailScreen`'s "Add to List" modal row convention). Already-reverted logs get no checkbox at all — replaced by an equal-width invisible spacer so columns stay aligned across rows — and are guarded against selection both visually and in the handler itself (`if (item.isReverted) return;`), not just by hiding the checkbox.

"Undo Selected" fires immediately with **no confirmation**, matching web exactly. "Reset All Data" reuses `handleDeleteAccount`'s exact `Alert.alert` destructive-confirm structure — the app's one and only such pattern — but deliberately does **not** call `logout()` afterward, unlike Delete Account: Reset clears content data (watchlist/ratings/favorites/logs), not the account itself, matching backend semantics (`resetData` never touches auth/session).

The backend's `details` string per log entry (e.g. "Rated movie 8/10") is fixed English baked in at write time — not translatable. Rather than render it as the primary label, a `getLogMeta(actionType)` helper (module-level, colocated in the screen file, mirroring `notifications.tsx`'s `getNotificationMeta`) supplies the real translated label/icon; `details` renders only as smaller muted secondary text, the same spirit as how raw backend error messages already appear as fallback text elsewhere rather than as fully-localized primary strings.

**Backend fix included**: `resetData`'s activity-log wipe filtered on `ActivityLog.deleteMany({ user: userId })`, but the schema field is `userId`, not `user` — the query matched zero documents, so activity logs silently survived "Reset All Data" despite that clearly being the intent. Fixed to `{ userId }`. (Double-checked the neighboring `Rating.deleteMany({ user: userId })` call in the same function isn't the same bug — `Rating`'s schema field really is `user`, so that one was already correct.)

### TV Time / Letterboxd Import
New `app/(app)/profile/import.tsx`, reached via a new row in `settings.tsx` below Activity Log — this is what makes Activity Log's `IMPORT_TVTIME`/`IMPORT_LETTERBOXD` `getLogMeta` cases (previously dead code, nothing created those logs yet) reachable for the first time. Import undo works for free through Activity Log's existing generic revert logic, no special-casing needed.

**Deliberately does not stream live progress**, a confirmed, explicitly-offered user scope decision — React Native's networking layer (and axios's RN adapter) can't incrementally read a streamed response body the way browser `fetch().body.getReader()` can, and native `EventSource` doesn't exist in RN at all. Web's import endpoints hold a POST open and write `text/event-stream` progress events (`res.write(...)` repeatedly, `res.end()` once at the very end) over the same response. `src/api/importService.ts` instead just awaits the full response — since the response `Content-Type` isn't `application/json`, axios never attempts to parse it, so `res.data` is the raw concatenated SSE string — then parses out the *last* `data: {...}` block that carries a `status` field (progress blocks never do), which is always the completion/error message since it's the last thing written before `res.end()`. This loses only the live percentage bar; the exact same final `importedMovies`/`importedEpisodes` counts web's progress bar ends on are recovered this way with zero backend changes.

New dependency: **`expo-document-picker`** — `expo-image-picker` (already used for avatar upload) is image-only, can't pick arbitrary `.zip` files. Uses `type: "*/*"` in `getDocumentAsync`, deliberately not `"application/zip"` — Android's MIME-type reporting for zip files is inconsistent across file managers/cloud providers (some report `application/x-zip-compressed` or `application/octet-stream`), so a strict OS-level filter risks silently hiding valid files with no error surfaced. Validates the `.zip` extension client-side instead (mirrors web's own `<input accept=".zip">` + JS extension check exactly).

A mobile-only warning callout (no web equivalent) tells users to keep the app foregrounded during the upload, which can take minutes for large libraries — backgrounding can suspend network activity on iOS/Android and silently interrupt it. Documented as a known platform constraint, not engineered around (a real fix would need native background-task APIs, disproportionate for this feature's value).

### Forgot Password / Reset Password
Two new screens under `app/(auth)/`: `forgot-password.tsx` (email → `POST /users/forgot-password`) and `reset-password.tsx` (code + new password → `POST /users/reset-password`), reached via a new "Forgot password?" `Link` on `login.tsx`. Both endpoints already existed on the backend, untouched.

The backend sends a **6-digit numeric code by email, not a URL/deep-link token** — so unlike a typical "reset password" flow, there's no deep-linking work at all: the user just types the code into the app. `reset-password.tsx` uses a single plain `TextInput` for the code (`keyboardType="number-pad"`), not web's six-individual-digit-box widget — mobile already established a simplified single-input OTP convention for `verify-email.tsx`'s identical 6-digit-code pattern, and this stays consistent with that rather than reintroducing web's more elaborate UI. `forgot-password.tsx` → `reset-password.tsx` navigation reuses the exact `router.push({pathname, params:{email}})` pattern `register.tsx` → `verify-email.tsx` already established for multi-step auth flows — two separate routed screens, not one stateful two-step component like web's `ForgotPasswordPage.jsx`.

### Setup Profile Onboarding
New root-level screen `app/setup-profile.tsx` — deliberately **not** nested inside `(auth)/` or `(app)/`, for a specific reason: `(auth)/_layout.tsx` force-redirects to `/movies` the instant `user` becomes truthy, which happens as a side effect of `verifyEmail()` succeeding. A child screen's own `router.push` can't reliably out-navigate that automatic layout-level `<Redirect>` — they'd race on the same render pass. So instead, `AuthContext.tsx` gained a transient (not persisted to SecureStore — resets to `false` on every cold start, which is correct since it should only ever be true immediately after a fresh verification) `needsProfileSetup` boolean, set `true` only inside `verifyEmail()`, with a `clearNeedsProfileSetup()` setter also exposed. `(auth)/_layout.tsx`'s redirect now checks it first: `user && needsProfileSetup` → `/setup-profile`, else plain `user` → `/movies` as before. A normal `login()` or `completeOAuthLogin()` never sets the flag, so returning users never see this screen — confirmed by inspection, not just by the happy-path test.

The screen itself reuses `edit.tsx`'s exact avatar-pick + save pattern (`expo-image-picker` with `allowsEditing:true, aspect:[1,1]` as mobile's crop equivalent to web's `ImageCropper.jsx` modal, then `uploadAvatar` + `updateBio` + `AuthContext.updateUser`) but skips `edit.tsx`'s `getUserProfile` fetch entirely — `user` is already fresh in context right after verification, and web's own `SetupProfilePage.jsx` doesn't pre-fill bio either (bio always starts empty here, matching web). "Finish" and "Skip for now" both end by calling `clearNeedsProfileSetup()` then `router.replace("/movies")` — Skip makes zero API calls, exactly like web's ghost skip button. No backend changes: this is a pure client-side UX nudge, reusing the identical `PATCH /users/profile/:id/bio` and `POST /users/profile/:id/upload-profile-pic` endpoints `edit.tsx` already calls — there's no `isProfileSetup` flag or dedicated onboarding endpoint on the backend at all, on web or mobile.

### Theme / Appearance Selection
The biggest of the three "small standalone items" by far — web's 9 DaisyUI themes (`forest` default, `dark`, `dim`, `black`, `luxury`, `dracula`, `sunset`, `synthwave`, `coffee`, switched via `data-theme` + `localStorage`, zero backend involvement) required real new architecture on mobile, not just a new screen: mobile previously had exactly one hardcoded palette (`src/theme/colors.ts`, the `forest` values only), statically imported by **60 files**, each baking `colors.X` into a **module-scope** `StyleSheet.create({...})` evaluated once at import time. Per the user's explicit choice (reactive/instant switching over a "restart to apply" shortcut), all 60 had to start reading the active palette from a hook and rebuild their styles per-render.

**`src/theme/palettes.ts`** replaces `colors.ts` entirely (deleted, no back-compat shim) — a `PALETTES: Record<ThemeName, ColorPalette>` with all 9 themes' actual DaisyUI 4.12.24 values (extracted from `node_modules/daisyui/dist/themes.css`, which stores every color as a bare OKLCH triplet — `oklch()` isn't parseable by RN's style processor at all, so every value was converted to hex first). `forest` is copied verbatim from the old `colors.ts` (zero visual change to today's default). The other 8 use DaisyUI's real per-theme `info`/`success`/`warning`/`error`, unlike `forest`'s own entry in this file, which keeps its original hand-guessed Tailwind-style hex (DaisyUI's `forest` theme never actually overrides those, so there was never a "real" value to match — the 8 new themes mostly do define their own, so those are used instead, for internal consistency). `border`/`placeholder` have no DaisyUI equivalent in any theme (pure invention, first introduced for `forest`) — derived for the 8 new themes via a small one-off blend script rather than hand-picked by eye.

**`src/context/ThemeContext.tsx`** — `ThemeProvider`/`useTheme()`, persisted via `expo-secure-store` (`STORAGE_KEYS.THEME`, same library/pattern as `LANGUAGE` and `TOKEN`/`USER`, no new dependency), resolved at boot via a new `resolveInitialTheme()` mirroring `src/i18n/index.ts`'s `resolveInitialLanguage()` — `app/_layout.tsx` gained a third `initialTheme` boot-gate alongside the existing `fontsLoaded`/`i18nReady` ones, same mechanism, not a new one. **Also relocates the app's global `Text`/`TextInput` `defaultProps` hack** (previously a one-time mutation in `app/_layout.tsx` baking in `colors.baseContent`/`colors.placeholder` for every plain `<Text>`/`<TextInput>` in the app that never set color explicitly — the vast majority of them). A one-time mutation can't react to a theme change, so `applyGlobalTextDefaults(colors)` now runs **synchronously inside `ThemeProvider`'s render body** (not a `useEffect`) — a deliberate, narrow exception to "no side effects during render": it's an idempotent global-object write, and running it in an effect instead would cause a one-frame flash of the old theme's text color on every switch, since children render before effects flush.

**Migrating the 60 files**: written as one careful, fail-safe Node codemod (locate the module-scope `const styles = StyleSheet.create(...)` via brace-matching, relocate it into the component body wrapped in `useMemo(() => ..., [colors])`, swap the static `colors` import for `useTheme()`) rather than 60 rounds of hand-editing — the script **skips and reports** anything that doesn't match its exact expected shape rather than risk silently mangling a file. 56 of 57 converted cleanly on the first pass; the skip (`ContentRail.tsx`, a generic `<T>` component whose signature the script's regex didn't match) and 4 files the script *did* touch but incompletely — `Skeleton.tsx`, `StarRatingInput.tsx`, `GroupCard.tsx`, `community/[slug].tsx`, `messages/_layout.tsx` — were fixed by hand. All five share the same root cause: **sibling components in the same file that reference the shared `styles`/a `colors`-derived constant, where the script only patched the first-matched function** (`Skeleton.tsx` exports 12 separate skeleton components off one style object — fixed via a shared `useSkeletonStyles()` hook each one calls; `StarRatingInput.tsx`'s inner `Star` helper got the same treatment; `GroupCard.tsx` and `community/[slug].tsx` each had a module-scope `CATEGORY_COLOR` map referencing `colors.X` directly — turned into a `categoryColor(colors)` function called via `useMemo` inside the component; `messages/_layout.tsx`'s `MessagesHeaderRight` header-button component needed its own `useTheme()` call). `CineGraphDonut.tsx` and `MatchPercentageRing.tsx` (the two `react-native-svg`-based components, passing colors as `stroke`/`fill` props rather than through `StyleSheet`) needed no hand-fixing at all — the script's `useMemo`/hook-swap for their `StyleSheet.create` blocks was sufficient, since their SVG props already read `colors` fresh every render. `CineGraphDonut.tsx`'s separate 8-color genre-slice palette (`SLICE_COLORS`) is **intentionally theme-invariant** — it matches web's chart regardless of active DaisyUI theme, by design, untouched here.

**Settings UI** — new "Appearance" section in `profile/settings.tsx`, between Language and Activity Log. Since RN has no CSS cascade (web's live per-card preview works by wrapping each theme card in `data-theme={themeName}` and letting DaisyUI's CSS variables do the rest — no such mechanism exists in RN), each theme card explicitly reads `PALETTES[themeName]` directly — not the active `colors` from context — to render its own 3-dot preview. Theme names are **not** run through `t()`, matching web exactly (raw `{themeName}` + a `capitalize` style) and mobile's existing precedent for brand/proper-noun-like literal values (native language names, "Letterboxd"/"TV Time").

### Offline Handling
**Tier 1 scope, an explicit user choice** — web has zero offline handling of any kind (confirmed: no `navigator.onLine`, no service worker, no PWA manifest anywhere in `frontend/`), so this is a mobile-only, greenfield design. Full scope would range from a simple banner up to a real offline-first architecture (cached-GET-fallback + a queued-write-retry sync engine) — the user explicitly picked the smallest tier: connectivity detection + a global banner + distinguishing network-vs-server error messages + making today's silently-failing mutations visible. Cached-data fallback and queued-write retry are **explicitly out of scope**, deferred to a possible future pass.

New dependency: `@react-native-community/netinfo` (`npx expo install`, resolved `12.0.1` for SDK 57) — no `expo-network` equivalent exists, this is the standard Expo-compatible connectivity library. New `src/context/NetworkContext.tsx` (`useNetwork()` → `{isOffline}`) treats `isInternetReachable === null` (common right after any state change, still probing) as *not* offline, to avoid banner flicker on normal transitions. New `src/components/OfflineBanner.tsx` renders a `colors.warning`-tinted bar (matching the Import screen's existing warning-callout convention) — mounted once in `app/_layout.tsx`'s `RootNavigator`, as a sibling above the `<Stack>` inside a `flex:1` wrapper (pushes content down rather than an absolute overlay, avoiding z-index/safe-area edge cases with modals). This is also the app's **first use of `react-native-safe-area-context`** — already a transitive dependency via Expo Router but never directly used until now — so `RootLayout` gained a `<SafeAreaProvider>` wrapper at the very top for `useSafeAreaInsets()` to work.

**Centralized network-vs-server error distinction** — rather than touching the ~49 existing `e?.response?.data?.message || t("fallback")` call sites across the app, `src/api/client.ts`'s response interceptor now enriches network-level failures (`!error.response && error.request` — no server response at all, vs. a real 4xx/5xx) with a synthetic `error.response.data.message` carrying a translated "check your connection" string. Since every existing call site already reads `e?.response?.data?.message` first, this makes all of them automatically show a real, accurate message on network loss instead of falling through to their own generic per-screen fallback — **zero per-screen changes needed**. Confirmed safe: grepped the whole app for any `error.response.status`/status-code branching (e.g. a 401-triggers-logout pattern) that this synthetic response object might interfere with — none exists anywhere.

**New global Toast system** (`src/context/ToastContext.tsx` + `src/components/Toast.tsx`) — no toast/snackbar mechanism existed anywhere before this; the only prior "visible feedback" idioms were inline `setError` text (wrong for a transient mutation failure — would need a full-screen error state or per-screen plumbing) and `Alert.alert` (too heavy/blocking for a failed tap on something like a like button, especially with several possible in a row while intermittently offline). `useToast().showToast(message)`, auto-dismisses after ~2.5s, small bottom banner fading via RN's built-in `Animated` (matching `Skeleton.tsx`'s existing precedent over adding `react-native-reanimated`).

**The real gap this tier targets**: a codebase-wide audit found **9 user-initiated action handlers across 5 files** that caught a failure with zero feedback at all (not even the generic fallback — pure silent optimistic-rollback, so a tap while offline just did nothing visible): `ContentDetailScreen.tsx`'s `handleRate`/`toggleWatchlist`/`openListModal`/`toggleListMembership`/`handleCreateAndAdd` (5), `ReviewCard.tsx`/`PopularReviewCard.tsx`'s `handleLike` (1 each), `useFollowState.ts`'s `follow`/`unfollow` (2 — these already called `setError(...)`, but the only consumer, `FollowButton.tsx`, never read or rendered it, making it dead code disguised as handled), and `network.tsx`'s `handleRemove` (1). All 9 now also call `showToast(...)` alongside their existing revert logic. **Deliberately left untouched**: every other silent catch in the app already had a justifying code comment marking it as a non-critical background/prefetch/poll operation (`loadReviews`/`loadFavoriteStatus`, `NotificationContext`'s poll, `ChatContext`'s background refresh, several prefetches) — adding toast noise to those would be over-engineering for this tier. `messages/new.tsx`'s debounced search-failure and `ChatRoom.tsx`'s message-send REST fallback were also deliberately left alone (the former to avoid toast-spam on every failed keystroke while offline, the latter because a silently-never-sent message deserves a real retry/failed-indicator affordance, not a toast — flagged as a good candidate for a *future*, larger offline tier, not dropped from consideration).

### Navigation architecture — read this before adding new screens
**Every tab is its own nested `Stack`**, not a flat screen (`app/(app)/search/_layout.tsx`, `watchlist/_layout.tsx`, `lists/_layout.tsx`, `profile/_layout.tsx`, `home/_layout.tsx`). This was a real bug that had to be fixed mid-build: bottom-tab navigators don't track per-tab history, so a flat shared screen's "back" always jumps to the *first* tab regardless of where you actually came from. It looked fine during early testing purely by coincidence (testing kept starting from the first tab).

The fix, and the pattern to follow for anything new: **Content Detail is duplicated as a thin route file inside every tab that links to it** (`search/content/[type]/[id].tsx`, `watchlist/content/[type]/[id].tsx`, `lists/content/[type]/[id].tsx`, `home/content/[type]/[id].tsx`, `profile/content/[type]/[id].tsx`), each just re-exporting one shared implementation (`src/screens/ContentDetailScreen.tsx`) — no logic duplication, just route registration. `ContentCard` (`src/components/ContentCard.tsx`) takes a required `basePath` prop (`"/watchlist" | "/to-watch" | "/lists" | "/home" | "/profile" | \`/user/${string}\``) so it knows which tab's copy of the route to push to. **If you add a new screen that links into a shared detail view from multiple tabs, follow this same pattern** — do not add a flat cross-tab screen to `(app)/_layout.tsx` directly.

**A second pattern exists for screens reachable from *everywhere*, owned by no single tab** — `notifications.tsx` and `network.tsx` are registered as **root-level** `Stack.Screen`s in `app/_layout.tsx` (outside the `(app)` tab group entirely) instead of being duplicated into every tab. `user/[id]/` (Public Profile) is the same idea taken one step further: it's *also* root-level, but since it needs its **own** Content Detail link (for Favorites), it's a directory with its own nested Stack (`user/[id]/_layout.tsx` + `index.tsx` + `content/[type]/[id].tsx`) rather than a single flat file — the root `Stack.Screen name="user/[id]"` entry just has `headerShown:false` and lets the nested Stack own its own header, the same relationship the root `(app)` entry has to `(app)/_layout.tsx`'s Tabs. Opening any of these from any tab and closing it correctly returns you to that exact tab, with zero per-tab duplication. Use this pattern, not the per-tab-duplication one, for anything reachable from more than a couple of unrelated places. The root `<Stack>` requires **all** its screens to be declared together once any one is explicit — a past bug (see the Notifications section above) came from adding one without the rest.

**Nesting a dynamic segment inside another of the same name is safe** (e.g. `user/[id]/content/[type]/[id].tsx`'s inner `[id]` vs. the outer `user/[id]`'s `[id]`) — `useLocalSearchParams()` is scoped to the current focused screen only, never merged with ancestor segments, so there's no collision. `lists/[id].tsx` + `lists/content/[type]/[id].tsx` already relied on this same fact before Favorites made it explicit.

## 4. API layer conventions

`src/api/client.ts` is a single axios instance: request interceptor attaches the JWT from `expo-secure-store`, response interceptor unwraps the backend's `{success, message, data, pagination?}` envelope so callers just get `res.data` (and `res.pagination` when paginated).

**Known envelope inconsistencies in the backend** — several endpoints don't follow that envelope, and the corresponding service functions read fields directly instead of relying on the interceptor:
- Watchlist (`GET/POST/DELETE /users/me/watchlist`) returns raw `{message, watchlist}`.
- `GET /users/profile/:id` returns raw JSON on both branches (authorized and masked/private).
- Custom Lists (`GET /lists/me`, etc.) return `{lists}` / `{list}` — works fine either way since the interceptor only unwraps when it recognizes the envelope shape, otherwise passes the object through untouched, and these services read `.lists`/`.list` off whatever comes out.
- Follow endpoints are the worst offender for this — `POST /users/remove-follower` and the accept/reject follow-request endpoints return raw `{success,message}` with no `data` key at all (not unwrapped); `GET /users/me/follow-requests` and `.../sent-requests` return bare arrays with no envelope whatsoever. See `src/api/userService.ts`'s per-function comments before adding more follow-related calls.

Each `src/api/*.ts` file has a comment noting when this applies. **If a new endpoint's response looks wrong (extra nesting, or fields missing), check whether it's actually one of these unwrapped-envelope cases before assuming a bug.**

## 7. Google Sign-In — read before touching this

This took several rounds of real debugging; the current setup is deliberate, not incidental.

**Backend** (`backend/routes/userRoute.js`, `backend/controllers/userController.js`): the existing Passport Google strategy and its registered `GOOGLE_CALLBACK_URL` (`http://localhost:5000/...`) are **completely untouched** — web login still works exactly as before. Mobile adds an *additive* path: `GET /api/users/auth/google?platform=mobile&redirectUri=<url>` threads the mobile app's own redirect URL through the OAuth `state` param (base64url-encoded JSON), and `googleAuthCallback` decodes it and redirects there instead of the web frontend, when present.

**Why not just point mobile at a fixed custom URL scheme** (`cinephix://oauth-success`)? Because **Expo Go can't register arbitrary custom URL schemes** — only a real standalone/dev-client build can. During development (Expo Go), `Linking.createURL()` produces a dynamic `exp://<lan-ip>:8081/--/oauth-success` URL instead, and the backend has to redirect to *that*, not a hardcoded scheme. This is why the redirect URL is passed explicitly by the client rather than assumed server-side (`src/api/googleAuth.ts`).

**Why the callback URL itself (`GOOGLE_CALLBACK_URL`) is NOT made dynamic per-platform**: Google's "Web application" OAuth client type flatly rejects private IPs (`192.168.x.x`) as registered redirect URIs — there's no way to register a LAN-IP callback at all. The workaround for emulator testing is `adb reverse tcp:5000 tcp:5000`, which makes the emulator's own `localhost:5000` forward to the host machine — letting mobile reuse the *exact same* already-registered `http://localhost:5000/api/users/auth/google/callback` as web, with zero Google Cloud Console changes. **This must be re-run every time the emulator restarts** (`adb reverse` doesn't persist). It does not help a physical phone with no ADB connection — see §5.
